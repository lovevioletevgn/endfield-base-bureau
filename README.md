python tools/ake.py 基地 --详细              # 据点发展等级逐级上限矩阵

python tools/ake.py 规则 无线               # 搜规则，附原文证据可复核
python tools/ake.py 数值                    # 列出所有带机制数值的设施

## 数据分层与版权（重要）

本项目的文件按**版权归属**分三层，这决定了哪些能进版本库、哪些不能：

| 层 | 内容 | 体量 | 进 git？ | 说明 |
|---|---|---|---|---|
| **① 游戏解包数据** | `raw/` —— 67 张 TableCfg | 18.4 MB | ❌ **绝不** | 含 `I18nTextTable_CN`（14.7 万条游戏内文案原文）。版权归鹰角网络，**不外传、不上云、不进版本库** |
| **② 烘焙产物** | `data/raw_baked.json` | 36 KB | ✅ | 从 `raw/` 提取的**派生参数**（环境色、散布机规格、5 条环境依赖配方、281 件可出货物品的 id/名/稀有度/域归属）。是「数据」不是「原文」，替代 14.3 MB 的 raw 依赖 |
| **③ 清洗后数据包** | `data/*.json` | 1.0 MB | ✅ | 结构化数据，本项目主体 |
| **④ 源码** | `tools/` | 847 KB | ✅ | 构建 / 测试 / 推送脚本 |

**为什么这么分**：`build_html.py` 原先直接读 `raw/` 做注入层加工。为把版权风险压到最低（2026-09-23 定策），把「raw → 注入字段」的加工抽成 `tools/bake_raw.py`，结果落到 `data/raw_baked.json`；`build_html.py` **优先读烘焙文件，缺了才回落读 `raw/`**。

**效果**：没有 `raw/` 的机器（云端开发环境、新克隆的副本）也能完整构建出**字节完全一致**的产物 —— 已实测 sha256 相同。

**怎么更新烘焙**（游戏版本更新后）：
1. 一条命令补齐 `raw/`：

   ```bash
   python tools/fetch_raw.py                              # 拉全部（已存在的跳过）
   python tools/fetch_raw.py --ver 1.6.0 --hotfix xxxxxxx-x  # 换游戏版本
   python tools/fetch_raw.py --only ItemTable RewardTable     # 只拉指定的表
   ```

   默认版本取自 `data/meta.json`，与当前数据包同源。底层是数据域直取：
   `https://data.akedata.wiki/public/<版本>/<hotfix>/TableCfg/<表名>.json`
   —— 该地址**不支持目录浏览**，只能按表名逐个取；脚本已内嵌 66 张表的清单，不用自己记；
2. 跑 `python tools/build.py`（会重建数据包并**自动刷新**烘焙）；
3. 或单独跑 `python tools/bake_raw.py`。

烘焙文件里记了 6 张源表的 `sha256_16` 指纹（`_rawFiles` 字段），可据此判断它是否与手头 `raw/` 同源。

> ⚠️ **不要手改 `data/raw_baked.json`** —— 它由脚本生成；改了也会在下次 `build.py` 时被覆盖。

### 云端环境的能力边界（重要）

因为 `raw/` 不上云（版权），**没有 `raw/` 的机器（云端 Codespaces / 新克隆副本）只能做以下事**：

| 能 ✅ | 不能 ❌ |
|---|---|
| 跑 `build_html.py` 生成成品 HTML（靠 `data/raw_baked.json` + `data/*.json`） | 跑 `build.py` 重建 `data/*.json` |
| 改 HTML 模板 / CSS / JS / 排布算法 | 跑 `bake_raw.py` 刷新烘焙 |
| 跑 `test_html.js` / `test_layout_events.js` 回归测试 | 拉取或更新 `raw/` |
| 改 `data/*.json` 的单条内容（手工编辑） | — |

**为什么**：`build.py` 需要读 **26 张** raw 表（`FactoryMinerTable`、`FactoryFluidPumpInTable`、`Spaceship*` 等），这些表的加工逻辑是过程式的，没法简单烘焙；且其中 `I18nTextTable_CN` 单表就有 11 MB —— 烘焙它等于把 raw 搬上云，**与版权策略冲突**。

**所以数据更新的正确流程是**：**游戏版本更新时在本地跑 `build.py`**（有 raw，全功能）→ 把重算后的 `data/*.json` 提交上来。日常改代码在云端即可。

## 📐 蓝图数据（搭生产线的核心）

### 单位口径 —— 先看懂这个，再看数据

| 字段 | 含义 | 能不能用于蓝图 |
|---|---|---|
| `range.width / depth / height` | **整数格**。宽×深=地面占格，高=占用格高 | ✅ **蓝图摆放依据** |
| `modelHeight` | 模型实际高度（**小数**，单位米） | ❌ 纯视觉，蓝图不要用 |

> 实测：天有洪炉 `modelHeight`=4.4 而 `height`=5，两者不是一回事。全局有 20 处不一致，**一律以 `width/depth/height` 为准**。

### 接口坐标 —— 决定"线怎么接"

每座建筑的 `inputPorts` / `outputPorts` 带每个接口的**格坐标**：

- `x` 沿 width 方向（0 ~ W-1）
- `z` 沿 depth 方向（0 ~ D-1）
- `y` 为高度层（如精炼炉的管道口在 y=3，地面传送带口在 y=0）
- `isPipe`：`true`=管道口，`false`=传送带口

**边名用格坐标（`z=0` / `z=D-1` / `x=0` / `x=W-1`），不是东南西北。** 配置表里没有证据能把 x/z 轴对应到游戏内的绝对方位，所以本库不声称方向。蓝图层面需要的信息（口在哪条边、每条边几个接口）完全不受影响。

> 角上的接口会同时命中两条边，因此各边计数之和大于接口总数。`mixedSides` 只在进/出料口占用**完全相同**的边集合时为 `true`。

### 占地平面示意：SVG 俯视图（2026-09-20 起取代 ASCII 字符画）

「占地蓝图」页展开任意一座设施，接口布局现在是 **SVG 俯视图**：网格 + 建筑外框 + 接口方块/圆点 + 朝外的接口引线，观感对齐游戏蓝图预览。

| 图形 | 含义 |
|---|---|
| 绿色实心方块 `I` | 进料口（传送带） |
| 浅绿圆点 `i` | 进料口（管道，虚线引线） |
| 棕色实心方块 `O` | 出料口（传送带） |
| 浅棕圆点 `o` | 出料口（管道，虚线引线） |
| 红色方块 `×` | 同格多口（多种/多个口挤同一格） |
| 外圈短线 | 口朝哪条边外 |

- **为什么不用游戏贴图**：游戏蓝图分享码解不开（见下一节），贴图有版权，而且要保持单文件离线可用。做法与社区工具一致 —— `zmd-bp-tool`、`t2blueprint`、`IndustrialPlanner`、endfieldtools 的工厂规划器全都是自己画矢量网格 + 建筑外框 + 传送带线，没人嵌游戏贴图。
- 颜色只表达 进/出 与 传送带/管道；边名仍是格坐标（`z=0` / `x=0` …），**不声称游戏内绝对方位**。
- 建筑本体按**分类配色 + 分类字标**（采/炼/组/流/电/储/御/饰），比纯白框更接近游戏卡面观感。分类色与字标是自绘的，不是游戏贴图。
- 测试有断言守着：确实是 SVG、接口形状数量 = 去重后的接口格位数、ASCII 版已移除。

### 布局试摆（交互沙盘，2026-09-20 新增，2026-09-21 加进阶操作）

「布局试摆」标签页：左栏点选建筑 → 右边画布点击摆放（吸附网格）。可以选画布尺寸 **40×40 / 50×50 / 70×70 / 80×80**（正好对应副/主基地边长），实时显示「已放几座、占地几格、剩余几格」。

**操作表**（2026-09-21 补）：

| 想干什么 | 怎么操作 |
|---|---|
| 摆放 | 左栏点建筑 → 点画布空白处（越界/重叠会被挡下并给提示） |
| 单个选中 | 单击已放建筑（选中态是暖色描边） |
| 删除单座 | 双击该建筑（或选中后按 `Del`） |
| 批量框选 | 在**空白处按住拖拽**出橡皮筋矩形，松手选中框内所有建筑 |
| 批量移动 | 拖住任意一座选中建筑，整组跟着走（碰撞会整组挡回） |
| 批量旋转 | `R`（或按钮）：绕选区外接矩形中心整体转 90°，**接口跟着转** |
| 复制一组 | `Ctrl+D`：整组往右让一个身位，右边放不下就往下，都放不下则提示 |
| 撤销 / 重做 | `Ctrl+Z` / `Ctrl+Y`（按钮上也有），栈深 80 步 |
| 加选 / 减选 | `Shift` + 单击 |
| 取消选中 | `Esc` 或点空白处 |

- **左栏默认只列「能进基地产线」的基建**（2026-09-21 需求）：**生产**（基础加工 8 + 组件加工 13）、**电力**（电力设施，见下）、**存储物流**（仓储物流 13 + 物流辅助 9），外加**核心结构 4 件**（协议核心 / 次级核心 / 产物排出口 / 污水接入口）—— 共 **50 座**。资源采集（矿机/水泵只能放野外矿点）、防御设施、装饰（田块/玩偶/立牌）默认不列；要单独看某类，用上方分类下拉选，左栏顶部有「回到默认三类」。

|---|---|---|---|---|

### 一句话版

| 问题 | 结论 |
|---|---|
| 传送带能建在野外吗？ | **不能。** 明文规定只在集成核心区域内允许建造 |
| 开采基建能建在主基地里吗？ | **进不去**——但不是被区域规则挡住，而是**矿机只能放矿点，矿点在野外** |

### 一、集成核心区域是"厂区"，野外不是

这是理解另外三条的**前提**。协议核心周围的划拨工业用地叫**集成核心区域**，它有自己的面积、设备数上限、传送带数上限。仓库存取线、息壤供电桩/中继器只允许放这里（或在区内享受无视距离自动连接）。

> 传送带是一种基础物流设备，作用是在设备间运输各种材料，**只限定在集成核心区域中才可以建设传送带**。
> —— 游戏内教学原文（两条文案互为佐证）

所以整张地图的逻辑是：**野外 = 只有采集点，厂区 = 有传送带**。中间那段路，就是下面两条规则要解决的。

### 二、开采基建：只能放矿点上，矿点在野外

配置表里**没有任何一条**写"矿机不得放置在集成核心区域"。真正的硬限制是：

> 矿机是用来开采矿物的设备，**只能放置在矿点上**。

三台矿机的 `desc` 全都这么写，而矿点（源矿/紫晶矿/蓝铁矿/赤铜矿、惰气/酸气）在文案里一律描述为"**分布在野外**"。主基地里没矿点，所以开采基建自然进不去。**结果与实测一致，但原因不是区域禁令。**

气体/液体开采设备同理——气体收集泵"放置在气体矿点上"，水泵/水驱矿机一样依赖矿点。

> **⚠ 别踩的坑：** `placeDomains` 字段里 `miner_1` 只有 `recommendDomains=['domain_1']`，这是"**推荐**地区"不是"禁止区域"。真正的区域禁令走 `placeDomains`（如 `log_hongs_bus`、`power_diffuser_2`、`xiranite_oven_1` 是 `placeDomains=['domain_2']`）。两个字段别混。

### 三、矿物无线传输：两条独立通路

#### 通路 A — 电驱矿机（`miner_2` / `miner_3`）

> 在**通电**后，电驱矿机会自行运转，并**每隔一段时间**将开采到的矿石**无线传输回仓库**。

- 默认就是「**无线传输模式**」，可切换为「**仓储模式**」（切了就只堆缓存区，必须手动取）
- 配置字段：`FactoryMinerTable.hasDroneMode = true`、`msTransferCD = 10000`（10 秒）

> ⚠️ **矿机的 3 个传送带出料口，实际上"没有用"**（2026-09-22 两度核实，并追问「那这样 4 还用吗，玩家都是用无线传输的」）。
> 配置表里它们确实记在 `ports`（`kind=output`、`medium=传送带`，`z=0` 边），但**两种模式都用不上**：
> 默认「无线传输模式」产物直接回仓库；切「仓储模式」也只是进缓存区、**手动取出**（文案原文：
> 「切换到仓储模式后，会和源石矿机一样不会将矿物送回仓库，**必须从缓存区手动取出**」）。
>
> | 矿机（**版本**） | 产物去向 | 依据 |
> |---|---|---|
> | 电驱 / 二型电驱矿机 | **无线回传仓库**（10 秒一次） | 配置表 `hasDroneMode=true` + 教学文案 |
> | **水驱矿机**（**1.1「新潮起，故渊离」·武陵工业二期**新增） | **同样回仓库** | **2026-09-22 实机确认** + 联网核实 1.1 版本公告；配置表里它**不在矿机表**中、没有该字段 |
> | 便携源石矿机 | 进**缓存区**、**手动收取** | `hasDroneMode=false`、`msTransferCD=0` + 文案 |
>
> 所以「占地平面示意」**不再画那 3 个口** —— 直接在建物上标 **⇡ 无线回传仓库**（水驱/电驱/二型电驱）
> 或 **⇥ 缓存区 · 手动收取**（便携源石矿机），图下写明实情与来源。水驱矿机的**管道进料口**（清水）是真口，照常画。
> 数据在 `mining_power.json → gather[]`：`wireless` / `wirelessSource`（配置表 | 实机确认）/ `msTransferCD` / `wirelessNote`；
> `ports` 仍保留（那是配置表事实），只是不画。
> （⚠️ 顺带一条版本更正：水驱矿机是 **1.1** 新增的，不是 1.5 —— 官方 1.1 公告：「开放武陵工业二期，新增赤铜矿物与水驱矿机采集玩法」。
> 所以"它不在矿机表里"与"版本新增"无关，别拿后者当解释。）

#### 通路 B — 协议储存箱（`storager_1` / `storager_nop_1`）

> 在**无线传输模式**下，**已通电**的协议储存箱可以将其内部存放的物品**远程传输到协议核心仓库**。

- **前提是通电**（供电桩/中继器接入电网）。未通电 = 不能传（"储存箱未开启无法无线传输"）
- 配置字段：`FactoryConst.domainTransportIntervalTime = 3600`、`domain2SpHubId = "map02_lv002_sp_hub_1"`

| 设备 | 为什么 |
|---|---|
| 便携源石矿机 `miner_1` | `hasDroneMode = false`、`msTransferCD = 0`，且文案写"请记得定期返回…**手动收取**"；产物进缓存区 |

> ⚠️ 2026-09-22 **两次更正**：
> ① **水驱矿机 `miner_4` 也把矿物送回仓库**（实机确认）。它曾被列进这张"不走无线"的表，
> 理由是"配置表里不在矿机表、没有 `hasDroneMode` 字段" —— 但**配置表没有该字段 ≠ 游戏里没有这个行为**，
> 别再拿"字段缺失"当成"功能不存在"。
> ② 它的版本我说错过一次：**水驱矿机是 1.1「新潮起，故渊离」新增的**（官方公告原话「开放武陵工业二期，新增赤铜矿物与水驱矿机采集玩法」），

> 所以占地示意**不画它们**了，改标 ⇡ / ⇥ 徽标。

#### 关键推论

**「无线传输」解决的是"野外 → 仓库"这一段。** 矿一旦到了仓库，在集成核心区域内**仓库与背包是连通的**，仓库取货口可以直接把它送上产线。**所以野外那一段完全不需要传送带/管道。** 这也解释了为什么野外没有传送带却不影响自动化。

### 四、气体液体：只能走管道（比想象中更硬）

曾有一种说法是"气体和液体要通过管道运输"——数据比这更硬：**它们连传送带接口都没有。**

从开采到进厂，全链路建筑的端口**全部** `isPipe = true`：抽出来是管口、运是管道、存是管口、用是管口。

**纯管道设备（无任何传送带接口）：**

| 设备 | 端口 |
|---|---|
| 水泵 `pump_1` / 二型耐酸水泵 `pump_2` | 输出 1 管口 |
| 气体收集泵 `gas_pump_1` | 输出 1 管口（免电） |
| 储气罐 / 储液罐 | 进 1 管口 + 出 1 管口 |
| 气体反应炉 `gas_reactor_1` | 2 进 2 出，全管口 |
| 气体散布机 `vaporizer_1` | 1 进管口，无出 |
| 给水器 / 洒水机 / 废水处理机 | 1 进管口 |
| 暗管入口 ×2 / 暗管出口 ×2 | 1~2 管口 |

**混合设备**（带口 + 管口并存，但**流体那一侧仍然必须走管**）：提纯机、反应池、扩容反应池、液气转化机、固气转化机。

跨区域则用**暗管**——官方文案写得很明确：

> 集成工业已通过**多口暗管**完成了**惰气矿区和集成核心区域的连接**。

暗管最大配对长度 **300 米**（`udPipeConnectMaxLength`），明显大于单条传送带（110）和单条管道（80）——**它就是为跨区域长距离流体运输设计的**。

> **附加限制：** 液体/气体的开采与加工还额外需要「**工业开采许可证**」，只在部分地区可用（`缺少液体开采许可，无法进行液体开采`）。

### 五、把三条串起来

```
矿点（野外）                          集成核心区域（厂区）
─────────────                        ──────────────────
矿机 ──无线传输──▶ 仓库 ─┐
                          ├─ 仓库与背包连通 ──▶ 取货口 ──传送带──▶ 产线
协议储存箱 ──无线传输──▶ 仓库 ─┘

气体收集泵/水泵 ──管道──▶ [暗管 ≤300m] ──管道──▶ 储罐/反应炉 ──▶ 产线
```

**固体走无线，流体走管道。** 这是同一套设计的两半——流体塞不进仓库的"物品"槽位，没有无线通路，只能物理运输。

### 六、跨地区传输（库存 / 超库存）—— 仓库不通，但能跨地区送货

仓库是**分地区**的：现在只有两个地区，四号谷地 `domain_1` 与武陵 `domain_2`，各自的仓库互相独立
（文案原文：`6487171838447479486`「各地区仓库是**互相独立**的」）。但两个仓库之间可以**传东西**。
**粒度是「地区」不是「基地」**：一个地区的几片基地**共享该地区这一个仓库**，不是每个分基地各配一个仓库
（2026-09-22 确认）—— 所以跨地区收发的收货方是「地区仓库」，同地区的基地都能从它取货。

入口在 **协议核心 − 协议管理**（`6213431956619667777`）。两种模式：

| 模式 | 行为 | 解锁条件 |
|---|---|---|
| **库存传输** | 在**起点仓库扣除**物品，等量送到终点仓库 | 起点地区「对应建设等级」 |
| **超库存传输** | **不扣起点库存**，终点直接获得；起点地区能产的**任意一种**物品都能传，且**不消耗仓库库存** | 起点地区「较高建设等级」（ `-4573223422367784963` / `359619165901015695` ） |

三条硬约束（排布器按这个算）：

1. **每批只能传一种物品**，数量上限 = **传输总值 ÷ 单位物品价值**（`-6087880617344615614` / `1845235994830423548`）。
   单位物品价值取 `FactoryItemTable.value`（这份数据已经进 `data/items.json`，字段 `value`）。
2. **传输总值取决于出发地（四号谷地）的建设等级**，且随等级提升而增加 ——
   ⚠️ **每一档具体是多少，配置表里没有**：`DomainDataTable.domainDevelopmentLevel` 每级只有
   `bandwidth / battleBuildingLimit / travelPoleLimit / isMineOutputUp` 四个效果字段，没有传输相关项。
   所以本工具**不瞎编档位数字**，改成让你把界面上看到的「传输总值」填进来，由工具反推数量与速率。
3. **一批要等一个间隔**：`FactoryConst.domainTransportIntervalTime = 3600`（界面文案是「%s 后可传输」，
   另有「当前剩余传输次数」）。间隔决定**供货速率**（个/分）= 每批数量 ÷ (间隔小时数 × 60)
   —— 例如每批 1500 个、1 小时一批 = **25 个/分**，跨地区收货**不是无限供**。
   ⚠️ v73 的实现漏除了 60（把「个/小时」直接标成「/分」，虚高 60 倍，「喂不饱」红字永不触发），v74 修正。
4. **解锁门槛与档位（2026-09-22 联网核实，配置表里没有的都用实机/社区实测补）**：
   - 地区建设 **8 级**解锁跨地区传输（库存传输，只能设一种物品；GameWith 与 game735 精华帖双源；
     smzdm 一处写 11 级，采信多数）；**12 级**解锁超库存传输（各源一致）。
   - **传输总值档位**：谷地 11 级 = **1200**、12 级满级 = **1500**（NGA 两帖 + GameRant 一致；
     1500/小时 ≈ value=1 的物品 25 个/分）。页面输入框示例值已从「如 3000」改「如 1500（谷地 12 级）」。
   - ⚠️ **升 12 级后协议不会自动切换**：11 级时设的「库存传输」会继续扣本地产，要手动改成超库存
     （NGA + smzdm 双源，都是玩家踩过坑的提醒）。
   - 中途取消传输再重设，**计时器重置回 1 小时**（GameRant，单源）。
   - 有 NGA 帖称传输**下线不运作、在线才推进**（单源，待实机确认 —— 若属实，离线挂机不产生跨地区供货）。

另外两条容易漏的：

- **能传的清单** = `FactoryItemTable.transferDomainIds`，**243 件，全部是「两地区通用」**（进 `data/items.json` 的 `domains` 字段）。
  野外采集物（惰气 / 惰性壤晶废液之类）不在清单里 → **传不了**，只能本地开采。
- **集成工业系统同时只在至多两个地区运行**（`-623612193743563597` 所在长文案）：
  地区一＝主线最新解锁的协议核心所在地区，地区二＝除地区一外最近停留的地区，其余地区暂时关停。
  → 所谓「多基地」实际是**两地联动**，不是 8 片基地同时开。

> 🔍 **查这类机制的教训**：传输这套东西在 `FactoryConst` 里只留了一个 `domainTransportIntervalTime`，
> 其余全在 **I18n 文案**里写得清清楚楚。**查跨系统机制要配置表 + I18n 双查**，只看配置表会以为它不存在。

#### 版本接口（`mining_power.json` → `ores`）

游戏更新时**只改数据、不改代码**：

| 字段 | 作用 |
|---|---|
| `schemaVersion` | 数据结构版本（当前 3） |
| `perNodePerMin` | **核心口径**：一个矿点 = 1 台矿机 = 满纯度 20/分 |
| `dataVersion` | = 游戏版本（构建时自动取 `GAME_VERSION`），页面顶部显示 |
| `beds[].pointsTotal` | 该矿种的**矿点总数** |
| `beds[].zones[]` | **按小地图**的点位（`zone` / `levelId` / `points`） |
| `beds[].mapMax` | **每个大地区的最大理论值**（逐区核对的那张表） |
| `beds[].theoreticalMax` | 游戏内「理论最大开采值」，带 `version` |
| `beds[].unaccounted` | 按区求和与理论值的**差额**（有差额就登记，不静默） |
| `beds[].mapMaxConfidence` | 每个大地区那个数是**实测**还是**推算** |
| `versionLog` | 逐版本记「这一版矿点/产量变了什么」 |
| `purityRule.zoneUpgrade` | 纯度与地区建设等级的**分区分级**关系 |

`build.py` 构建时跑**自洽自检**：按区求和 ≠ `zonesSum`、`mapMax` 合计 ≠ 理论值、点数×20 对不上 —— 任一项不成立就当场报错。
（这条护栏是四次算错的代价换来的：960 倍率错 → 清波寨当全图 → 每脉 2~6 点虚高 2~6 倍。）

### 单基地优化（路线图 ③ 第一梯队 · v50）

- **走线**：BFS 升级为 **Dijkstra（状态含方向，转弯罚 +2）**——路径又短又直；管线「由短到长」铺（流体优先，防被带子截断）
- **参数搜索 + 按分择优**（v52）：间{4,3,2} × 按列对齐{关,开} × 通道{5,3} 共 12 组全摆一遍打分，
  按「连通段 > 手动连 > 总线长」选高者，生成消息报搜索结果。实测铁制零件@10：管线 10→6 格（-40%）
- **层内主动换行**（v63）：上游比下游宽时（12 台块机 vs 6 台罐机），机器按下游分组、
  组的 x 对齐下游机器、冲突下沉一行——实测赤铜耐压罐@30 手动连 **15 → 0**、高度 90→54、线长再降 25%
- **桥接器**（v53，参照 IndustrialPlanner Connector 规则）：已铺线格允许「正交直穿」，
  穿越格自动铺**物流桥 / 管道桥**（桥上不转弯、一格桥只跨一条线）。
  实测赤铜耐压罐@10：2 条被围死的管道全部救回（手动连 2→0、全连通）
- **分流器语义标注**：1 进 3 出是 round-robin 轮询均分（参照 IndustrialPlanner 仿真内核），不是按需分配

  拿准入口点带/管格 → **替换**那段（串进线里）；拖动已摆的桥/准入口同理

### 局部锁定（路线图 ⑤-1 · v64）

「锁住满意的机器，只重排其余」—— 手调好的那几台，再也不会被下一次生成冲掉。

- **怎么锁**：选中件 → 工具栏「**锁定选中**」（或按 **`L`**）→ 变成**双线铁灰 + 右上角小锁**；
  「解锁选中」精确解锁、 「解锁全部」一键放开（都进撤销栈）
- **交互保护**：锁定件**拖不动 / 删不掉 / 转不了 / 不参与复制**，双击也不会误删；
  锁定件（含手拉的线）不会被分/汇流器替换或叠桥
- **重排其余**：排布器那一栏的按钮 —— 锁定机器当**固定件**（位置一格不动），
  其余机器重新分层摆位并**绕开**它们，管线整条重铺
- **口径**：交给布局的台数 = 树节点台数 **−** 已锁台数，锁定件自己拼回摆放列表
  → **机器总数守恒、产量口径不变**；画布上不归排布器管的散件原样留在原地，并被当障碍避开
- **已知边界**：锁定只对**机器**有意义 —— 管线是算出来的产物，重排时一定重铺（按钮与提示都写明了）

### 分流器：按「每 3 台下游一个」并排摆（路线图 ⑤-2 · v65）

分流器是 **1 进 3 出** —— 一台上游机器要喂 5 台下游，就得摆 **2 个**（各占上游一个出料口）。

- **以前只摆一个**：第 4 台下游起**既不接线也不报警**，报告里还写着「手动连 0 条」，看着像全连上了
  （实测「工业爆炸物@5」5 台下游只连上 3 台）。现在**每 3 台下游并排摆一个**分流器。
- **口径修正**：提示里的「需要几个分流器」原来按「缺几个出料口」算（`outNeed − outCap`），
  量级不对 → 现在按 `ceil(下游台数 / 3)`。
- **不再静默丢**：新增 `route.stats = {split, merge, dropped}`；凡是有线没连上，报告都会**逐条点名**
  （「还有 N 台下游没连上」），生成消息里也报实际摆放数「汇流 X / 分流 Y」。
- **真实触发工况**（扫全库找出来的）：**工业爆炸物 / 实验玉铜发散器 / 息壤玉葫芦** —— 都是
  「1 台高产能上游喂 5~10 台下游」。实测**息壤玉葫芦@5：分流器 2 个 → 5 台下游全接上、零手动连**。

### 高产能 / 宽链的连通率（路线图 ⑤-3 · v66）

先扫全库 52 个中大型工况量出短板，再逐个候选拆分数找根因 —— 两个：

| 根因 | 修法 |
|---|---|
| **打分口径反了**：2 条手动连只罚 200 分，盖不过 300 格线长差 → 「全连通但线长」被判输 | 手动连权重 **100 → 400**（少一条线是玩家得动手补的功能缺陷，多铺格子只是效率问题） |
| **参数网格太窄**：机器间距只到 4，而宽链要 **间 8** 竖缝才够并行走线 | 加「**失败驱动宽间距扩搜**」——只在最优方案还有手动连时才补跑，快路径一分钱不花 |
| 汇流器 **fanin=3** 没算进 T；下游口不够时还死守「省 ≥4 才并」 | 并线时把 T 抬到 `⌈N/3⌉`；**下游口不够 = 并线是"必须"不是"划算"** |

**效果**：全库 52 个中大型工况里**零手动连 51 个**（改前 44），手动连总数 **23 → 1 条**。
赤铜耐压罐@30 **手动连 0**（且改用「间8/分层对齐」后**不再需要汇流器**，线 463 格）；液化息壤@10（5 依赖混合链）从 6 条压到 1 条。
耗时：普通链不变，难例多花 1~2s（3.4~4.1s）。

### 原料侧闭环（排布器报告里）

报告现在会把「这条产线需要多少原料」推成野外侧的动作：

- 需 **几台矿机**（需求 ÷ 20/分，向上取整）+ 用的是哪种矿机
- **哪个区的矿点够**（按点数降序列出可选区 + 合计够不够 + 占用比例）
- 水驱矿机 → **耗水 20/分·台** → 需几台水泵（60/分·台，1 泵最多带 3 台）

**水与电的配比清单**（2026-09-22 补，口径：**1 台水泵最多带 3 台水驱矿机满效率**）：

- 水驱矿机台数 × 20/分 = 总需水 → 泵台数 = `⌈台数 ÷ 3⌉`（水泵 60/分·台）
- **分管建议**：前 N−1 台泵各带 3 台、最后一台带余数；**每台泵 60/分 < 管道上限 120/分 → 每台泵 1 条管道就够**，不用并联
- **供电**：水泵要通电（10 电/台）；水驱矿机**靠清水自供能、不耗电**；电驱矿机 5/10 电/台（野外要拉电或就近放供电桩）

### ④ 的边界：野外段的「摆放与走线」**不做**（不是遗漏）

2026-09-22 复核「那这样 ④ 还用做吗」—— 结论是**不用按原样做**，两条原因：

1. **野外没有需要连的线**：三种矿机的产物都是**无线回传仓库**（水驱 / 电驱 / 二型电驱）或**缓存区手动取**（便携源石矿机），
   每个矿点独立放一台就完事 —— 没有连线、没有避让、没有优化空间，也就没有"排布问题"。
2. **野外不是网格**，配置表里也没有地形与障碍（只有单段线长上限：供电桩 `autoConnectLength` **30m** / 中继器 **80m**）——
   水管怎么绕、电从哪拉，只能看那一片地形长什么样。

⇒ 路线图 ④ 的「**矿点逐点坐标**」与「**供水管网走线**」在本工具里**标为不做**；能做的**配比清单**（上面那三条）已经给出。

### 多目标共享中间产物（路线图 ⑥-2 · v76 —— 只建一套，再分流）

工具栏「＋ 目标」可给产线**再加最多 3 个目标**（各填一个 速率/分）。所有目标进**同一张需求 DAG**：
共用中间料只建一套产线，出料再分流给各目标 —— 不用为每个目标把同一条上游链各摆一遍。

- **合并重算**：共享节点按「各目标需求之和」重新上机器台数（⌈需求 / 单机速率⌉，整台实出），
  深度取最深消费者 +1；两轮推演（原始 / 带进货）口径不变；「进货不落地」等原有开关照常生效。
- **不保证省机器**：整台进位不重合时，合并台数 = 分开建之和；省的是**同一套上游只摆一遍**
  （一条矿线、一套水线），进位恰好重合时还能更少。测试锁的口径是「合并 ≤ 分开之和」。
- **报告**：头部目标列表（「 ＋ 」连接）；新增**共用中间料**段（几台 · 合并需求 · 整台实出 → 分给谁多少/分）；
  原料取各目标并集；管线明细里共用节点按消费者各一行。
- **实测**：赤铜耐压罐@10 ＋ 赤铜瓶@10 → 共用赤铜块 8 台（合并需求 40/分）、共用清水 8 台。
  ⚠️ 这种双目标长链默认 50×50 画布放不下，换 80×80。
- 验收：`test_html.js` 620（+20，含 ⑥-2×⑥-1 组合：收货吃合并需求 40/分、共用段与收货段同屏），`test_layout_events.js` 72。

### 跨基地选点（路线图 ⑥-3 · v83 —— 分配建议器，⑥ 收官）

## 🧩 蓝图分享码：能从数据里拿到什么

游戏内的**蓝图分享码**（形如 `EF01u289AA6uu0eEAoOU`，部分区服前缀 `EFO01`）是真实系统，但**不要指望从配置表解码**：

从 `FacBlueprintConst` 能确认的**只有约束条件**：

| 项 | 值 |
|---|---|
| 码前缀 | `EF01` / `EFO01` |
| 码字符集 | `AEIOUaeiou0123456789`（**不含小写 l**；易混的 0/O、1/I 是主要误输来源） |
| 蓝图最大范围 | **50 × 50 格** |
| 单蓝图节点上限 | **160** |
| 我的蓝图上限 | 100 |
| 赠送上限 | 100 |
| 分享码有效期 | 259200 秒 = **3 天** |
| 名称 / 描述上限 | 15 / 50 字 |
| 标签上限 | 5 |

> ⚠️ **码本身的编码规则不在配置表内。** 全网也没有公开的解码器 —— 现有的第三方蓝图工具（如 `eddy3721/arknights-endfield-bp-tool`、`XiaHouSheng/t2industry`）都用**自定义格式**，前者靠手动画布、后者靠**截图图像识别**，都无法导入游戏原生码。
> **结论**：蓝图码在本库里只能当**不透明字符串**处理，做不了结构化索引。要拿到"别人怎么摆的"，只能人工录入或走图像识别。

## ⚠️ 数据边界（重要）

**这个库只收录游戏配置表（TableCfg）里的静态数据。**

> ⚠️ **唯一的例外：`bases.json` 里的建设区域面积**（70×70 / 40×40 / 80×80 / 50×50 与单边存取口路数）。
> 那几个数字是**社区实测**，配置表里没有，见「基地面积与建造上限」一节。除此之外全库都是配置表数据。

**拿得到**：设施名称与官方术语、耗电、**协议容量**、**占地格数（宽×深×高）**、**物流接口格坐标与所在边**、**传送带/管道吞吐速率与连接限制**、配方输入输出、耗时、建造材料、地区归属、科技树分组、描述文本中的射程/间隔/攻击力。

**拿不到**（运行时数值，不在配置表内）：
- 矿脉纯度产率（低纯度 10 / 高纯度 20 矿每分钟）—— *注：矿机自身速率 20/min 已在库内*
- 建设值 / RDM 的具体收益数值
- 地区建设等级（RDL）的加成明细
- 同时只有两个大地区产出的判定逻辑
- 蓝图分享码的**编码/解码规则**（只有字符集与长度约束）

这几项**仍需游戏内实测**。本库不能替代现场验证，只能解决「术语叫什么」「配方要什么材料」「这个塔多少攻击力」「这块地放不放得下」这类静态问题。

### 蓝图层面还有哪些做不到

- **不能给出"最优布局"** —— 配置表只描述单个建筑的占格与接口，建筑之间的相对位置是玩家决策，不在数据里。
  > **全网核查结论（2026-09）**：没有公开的结构化布局数据库。社区有蓝图方案站（Talos Pioneers / endfieldtools.dev 等，各数百至近千条，带占地尺寸标签），但**存的是不透明分享码**，无法批量解析成坐标数据；中文侧多为"只列一串码"的帖子。产线配比有经验值（如「采矿机 20/min，一条带 30/min」——本库已用配置表数据交叉验证），但**没有公认的标准模块尺寸**。
- **不能证明绝对方位** —— `x`/`z` 是建筑自身的局部坐标系，全局朝向需要游戏内对照。真要严格对齐，建议拿两个已知朝向的建筑在游戏里比一次。
- ~~**不覆盖传送带/管道本身的占格与连接规则**~~ → **已解决大半，见上方「物流规则」章节**。吞吐速率、连接长度上限、角度限制、分流汇流端口、阀门档位、采掘/抽水速率**都已收录**。
  > **仍缺**：传送带/管道**在蓝图中占几格**（配置表无独立占格字段，按路径逐格铺设），以及**吞吐的游戏内实测校验**。

## 维护与更新

游戏版本更新后重新构建：

```bash
# 1. 拉取新版数据（先看 manifest 确认版本号）
curl https://data.akedata.wiki/manifest.json

# 2. 改 tools/build.py 顶部的 GAME_VERSION / HOTFIX / DATA_VERSION
#    并更新 raw/ 下的 json（路径形如 public/<版本>/<hotfix>/TableCfg/<表名>.json）

# 3. 重建
python tools/build.py          # 内部会依次跑 build_logistics / build_rules / build_bases
python tools/build_html.py
node tools/test_html.js        # 改完必跑，见文末
```

数据域路径规则（来自 AKEDatabase 的 `ake-data-source.js`）：

```
TableCfg:  https://data.akedata.wiki/public/<gameVersion>/<hotfix>/TableCfg/<表名>.json
Json:      https://data.akedata.wiki/public/Json/<文件名>.json
文本:      TableCfg 下的 I18nTextTable_CN.json（14.7 万条）
清单:      https://data.akedata.wiki/manifest.json
```

> ⚠️ `manifest.json` **只有版本号，没有表清单**——想找某张表只能靠猜表名。替代方案：直接列上游仓库拿到**全部 561 张表名**：
> ```
> https://api.github.com/repos/XiaBei-cy/EndfieldData/contents/TableCfg
> # 原始文件（注意分支是 master，不是 main）
> https://raw.githubusercontent.com/XiaBei-cy/EndfieldData/master/TableCfg/<表名>.json
> ```
> 本次物流数据就是靠这个清单找到的——**别再靠关键词猜表名了**。
>
> ⚠️ **拉表的源优先级**：`data.akedata.wiki` → jsDelivr → `raw.githubusercontent.com`。
> 实测连续拉十来个文件后 raw.githubusercontent 会 `RemoteDisconnected`（限流），
> data.akedata.wiki 反而稳。批量拉表时按上面顺序逐个 fallback，别死磕一个源。

## 🔧 审计与回归（2026-09-19）

### 回归测试：`tools/test_html.js`

改完 `build_html.py` 或 `data/` 之后**必须跑一遍**：

```bash
node tools/test_html.js 终末地基建查询.html
# 期望输出：RESULT pass=NN fail=0   （当前 633/633，另有事件层 72/72）
```

> ⚠️ **它把 `const`/`let` 换成 `var` 才能在沙箱里取全局 —— 这会掩盖块级作用域错误。**
> 2026-09-22 实测踩到：`RwRoute` 里 `const outNeed` 写在 `if` 块内、却在 `else if` 里引用，
> 两套测试全绿，**真机一跑 `LawRun` 就 `outNeed is not defined`（排布器整个点不动）**。
> 现在脚本尾部多了一道「**用原始代码（const/let 版）另开沙箱冒烟跑关键路径**」的门禁（+6 条）守着这类问题。

它在 Node 的 `vm` 沙箱里加载生成的 HTML，真实调用各页面的 `render()`，然后断言 **每一个筛选器候选项都必须产出非空结果**。

**为什么这条断言最重要**：筛选器以前是手写的固定列表（例如配方页写了 8 个分类，实际只有 3 个有数据，点剩下 5 个永远是空的；建筑页的地区列表漏了「四号谷地」）。这类 bug 不会报错、不会崩溃，只会安静地给出空页——**人眼几乎发现不了，但数据驱动的断言能**。

现在 `f1Html()` 的所有候选项都从 `DB` 里推导（`uniq()` 去重 + 排序），不再手写。

> 该脚本用**故障注入**验证过有效性：往候选项里塞一个不存在的分类，测试立刻报 `pass=90 fail=1` 并以退出码 1 结束；恢复后回到全绿。

**2026-09-20 追加的断言**（随「基地面积」页一起加，共 +20 条）：

- 基地页含 70×70 / 80×80 / 4900 / 6400 / 区域扩大 / 据点发展等级 / 蓝图最大宽度
- **基地页必须同时出现「社区实测」和「配置表」两个词** —— 防止把实测面积和配置表数据混着写（这页最容易犯的错）
- 基地页必须有「数据边界」段
- `bases.json` 面积条目正好 4 条；每个可扩建建造区正好 2 档「区域扩大」
- 切换据点筛选（四号谷地 / 武陵）后仍要有建造区输出
- **内联 JSON 最长行 < 8000 字符** —— 防超长单行让内嵌 webview 白屏（历史上翻过车）
