# 最优排布 · 设计规格

> 2026-09-24 起草。目标读者：博士（唯一使用者 / 决策人）与后续维护者。
> 本文是「一键基建最优排布 + 地区内多基地多画布」的需求规格与分期设计。
> 口径约定：**本文只写行为契约与验收判据，不写具体函数名/类名**（实现细节进代码注释）。

## 一、现状（2026-09-24 实测，非推断）

| 事实 | 依据 |
| --- | --- |
| 一个地区 4 个基地（1 主 + 3 副）：四号谷地主 70×70、副 40×40；武陵主 80×80、副 50×50 | `data/bases.json` `maxBases` / `baseRoleNote` |
| 可用格数（扣协议核心本体）：谷地主 4819 / 副 1600，武陵主 6400 / 副 2500 | `maxBases[].area.usableCells` |
| 选基地会自动把画布边长设成该基地边长 | 选基地分支 `L.size = 该基地 side` |
| 所有排布计算都以「单画布边长」为界 | 摆位 / 连线 / 越界判定全部吃同一个尺寸变量 |
| **已具备**：地区级选点 + 基地级落位建议 | `RxlBest`（2^N 穷举分配，成本 = 收货冲突×1000 + 喂不饱×300 + 重复建共享料×10 + 矿缺口）；`RxlRowHtml` 已给出「建议「枢细区·主基地」（可用 4819 格）」 |
| **缺口**：选点结论不落画布；一次只能处理一张画布 | 选点建议只出文案 |
| 面积估算为 `机器格数 × 2.2`，**非实测** | 估算字段，含物流件/通道的粗估 |

**影响面**：单画布状态字段在 `build_html.py` 中有 **142 处**引用 —— 直接改数据结构 = 高风险。

## 二、「最优」的可验收定义（本节是全案的判据源头）

博士原话：「这个地区最有效率，生产速度最快最省电，基建占地面积最少，我选择的几样物品产量最高的基建摆放」。

转成可验收判据（**约束 + 优化**两层，避免"多目标互相打架"）：

### 2.1 硬约束（必须满足，不满足即方案无效）

- **C1 产量达标**：博士选定的每一样物品，实际产能 **≥** 其指定速率（个/分钟）。
- **C2 落位合法**：每台机器都摆在其所在基地的建设区内，不越界、不重叠、不压建筑；物流件合法连通。
- **C3 地区限定**：只使用该地区允许的机器（地区限定机种如天有洪炉等在另一地区为**硬否决**）。
- **C4 协议容量不超上限**：每个基地的协议容量占用 MUST 不超过该基地的上限（谷地主基地 200，副基地按其档位）——
  这是硬墙，超了根本建不了，必须逐基地校验。
- **C5 专项建筑上限**：若用到防御建筑 / 滑索，MUST 不超过该基地的对应上限（配置表逐档给出）。

### 2.2 优化目标（在满足 C1~C3 的所有方案里比高低）

按**优先级**逐层比较（前一层相同时才比后一层，零加权魔法数字）：

1. **总用电最少**：该地区全部机器的用电之和最小（博士 2026-09-24 定为第一优先）。
2. **总协议容量最少**：该地区全部机器的协议容量占用之和最小（博士 2026-09-24 增补）。
3. **总占地最少**：该地区全部基地的机器实际占格数之和最小（按实际摆放计，不用 ×2.2 估算）。
4. **物流线总长最短**：传送带 / 管道的合计格数最少（少绕弯、少用料）。

> **为什么容量是独立维度**（2026-09-24 查数据后确认，起初我判断它是「台数的别名」，错了）：
> 54 座生产建筑的容量**一律是 2**，看似「容量 = 2×台数」；但**同物品存在单台产能差 2 倍的配方**，
> 于是台数不同、容量就不同。最尖锐的一例 —— **赤铜块**：
> 精炼炉 5/分·耗电 5（产 30/分 要 6 台 → 容量 12、用电 30），
> 固气转化机 10/分·耗电 50（要 3 台 → 容量 6、用电 150）。**用电与容量精确反向**，
> 所以「用电优先」的实际含义是：**优先省电，接受更高的容量占用**。
> （197 种主产物中有 7 组存在这种产能差。）
>
> **容量还会比面积更早到顶**：8 片基地里 4 片是容量先到 —— 枢纽区容量只够 100 台而面积能摆 192 台；
> 谷地通道容量 100（50 台）、首墩/应龙关 180（90 台）。因此 C4 的硬约束校验与**占用可视化**都是必须的。

> **与既有「配方选择」口径的关系**（v136 定，有回归锁）：单个物品选哪条配方，仍按
> 「单位原料成本 → 每轮耗电 → 单台产出」三层分层比较，**不改**。
> 本节的优化层用于比较**整体方案**（分到各基地 + 怎么摆）。
> 两者可能给出不同答案（例：省电的低耗机种可能占地更大），此时以**本节优先级**为准 ——
> 即：整体层面用电优先，允许为此付出更多占地。

> **原设想的第三层「机器台数最少」已撤掉**（2026-09-24 博士：「台数看不懂」→ 复核后确认该层冗余）：
> 台数与占地高度重合（机器少了占地自然少），单独成层没有独立信息量；
> 而**同样 3 栋机器，走线好坏能让物流线用量差近一倍** —— 物流线总长才是独立且真花钱的成本项。

> ⚠️ 「最快」在游戏里**不是可优化项** —— 规划器里的产能是稳态理想值，机器只要不停机就是满速。因此「生产速度最快」的正确落法 = **C1 硬约束**（速率达标），而不是一个可以往上优化的目标。这一条需要博士确认（见第六节 Q1）。

### 2.3 不追求的东西（明确不做）

- 不追求「塞进最少基地」，也不追求「单基地内最紧凑」—— 优化目标是**该地区合计**，不是单片最优。
- 不做机器运行时序仿真（排队 / 堵料堆积），沿用既有「单线负荷上限判定」口径。
- 不做供电覆盖范围校验（射程属关卡场景数据，配置表没有）。

## 三、总体路线（4 期，每期独立可验收）

| 期 | 交付 | 是否碰排布算法 |
| --- | --- | --- |
| **1** | **多画布架构**：一个地区 4 张画布全部可见、可切换编辑，每基地独立内容/撤销/方案快照 | **不碰**（回归锁保证单基地行为一字不差） |
| 2 | **基地级分配**：把 N 个目标分到 4 个基地（复用既有产线展开；共享中间品只建一套，跨基地靠仓库转运） | 新增函数，不改旧函数 |
| 3 | **一键生成**：逐基地跑摆位 + 连线并落到各自画布；摆不下时如实报告并给微调建议 | 复用，不改 |
| 4 | **跨基地转运清单 + 带宽校验**：列出「A 基地 → 仓库 → B 基地」的每种料与流量，按存取口路数（谷地主 23 / 副 13，武陵主 26 / 副 16 路）校验是否吃得下 | 新增校验 |

**依赖关系**：1 → 2 → 3 → 4。第 2 期起才需要分配算法；第 1 期是纯架构地基。

## 四、第 1 期 Spec（本轮实施范围）

### 4.1 Proposal

- **Intent**：让布局试摆页从「一次一张画布」升级为「一个地区多张画布」，使后续的一键最优排布有落点。
- **Scope**
  - In：多基地状态容器与活跃基地切换；该地区全部基地画布同时可见；点击切换编辑目标；每基地独立的选中/撤销/方案快照；自由模式（不选基地）行为完全不变。
  - Out：分配算法、一键生成、转运带宽校验、跨地区任何改动、单基地内的排布算法本身。
- **Approach**：多基地数据集中存放，**活跃基地的字段对外呈现为同一套字段**，使既有 142 处状态引用无需改动；渲染上「活跃基地全尺寸可编辑 + 其余基地缩略图」，避免近万个格子同时进 DOM 造成卡顿。

### 4.2 Requirements

**R1** 选择某基地后，该基地已摆放的内容 MUST 被保留；切走再切回，内容与位置 MUST 与切走前完全一致。

**R2** 每个基地 MUST 拥有相互独立的：摆放内容、选中集合、产线方案（含评价分数）、协议核心出货口设置、镜头旋转角。

> **撤销/重做不在此列 —— 它是全局操作历史**（2026-09-24 Wave 1 修正）：
> 既有断言要求「撤销切基地」能跨回上一片基地（并把画布尺寸一起退回去）。若改成每基地一栈，
> 这个语义就断了。快照里本来带 `base` 字段，全局栈天然支持跨基地回退。

**R3** 未选择基地（自由模式）时，系统行为 MUST 与本次改造前完全一致（含画布尺寸档位、越界判定、清空/撤销语义）。

**R4** 布局试摆页在该地区 MUST 同时呈现全部基地（1 主 + 3 副，各按其建设区尺寸），并可指定其中之一为编辑对象。

**R5** 一键生成/清空等既有操作 MUST 只作用于当前编辑对象，不影响其他基地内容。

#### Scenario 1（R1 / R2 · 主路径）
- GIVEN 已选四号谷地·枢纽区并在画布上摆了 3 台机器、执行过 1 次配方选择
- WHEN 切到谷地·谷地通道，再切回枢纽区
- THEN 3 台机器仍在原坐标、配方选择仍生效、撤销栈仍可撤回上一次操作

#### Scenario 2（R3 · 兼容边界，最容易出事）
- GIVEN 自由模式（未选基地）画布 50×50
- WHEN 依次执行 摆放 / 拖动 / 旋转 / 撤销 / 重做 / 清空 / 一键生成产线
- THEN 每步结果与改造前**逐项一致**（由既有 802 条回归锁逐条守住）

#### Scenario 3（R4 · 多画布呈现）
- GIVEN 已选地区为四号谷地
- WHEN 进入布局试摆页
- THEN 页面上同时能看到枢纽区 70×70、谷地通道 40×40、源石研究园 40×40、供能高地 40×40 四张画布，每张带基地名与主/副标识

#### Scenario 4（R5 · 作用域隔离）
- GIVEN 枢纽区摆了 3 台、谷地通道摆了 2 台，当前编辑对象是枢纽区
- WHEN 点「清空」
- THEN 只有枢纽区的 3 台被清掉，谷地通道的 2 台不受影响

### 4.3 关键设计决策

- **Decision 1：状态容器集中 + 活跃基地对外同形**
  - Reason：142 处状态引用若逐个改写，等于全量重构，回归风险不可控。
  - Alternatives Considered：① 把 `objs` 直接改成「每基地一份」并逐处改写调用点；② 每个基地各存一套全局状态对象，切换时整体替换。
  - Rejected Because：① 改动面 142 处、且大量在渲染与交互热路径上，回归锁只能覆盖行为、覆盖不了遗漏；② 与 ① 同类问题，且容易出现"两个基地共享了同一个数组引用"的隐蔽 bug。
  - Trade-offs Accepted：
    ① 活跃基地的字段是「当前指向」的，任何跨基地的批量读取都必须显式写明取自哪个基地（靠约定 + 注释，无类型保护）；
    ② **赋值顺序变得有意义** —— 「先写字段、再切基地」会把值写进旧格子。Wave 1 实测踩了**两次**
       （`Lsize` 与 `Lapply` 撤销恢复），凡「切基地 + 写字段」的组合一律**先切后写**。
  - Revisit When：若第 2 期分配算法需要频繁跨基地读写，改为显式「按基地取状态」的 API。

- **Decision 2：页签切换（一次只渲染一张）+ 页签自带摘要**（博士 2026-09-24 拍板）
  - Reason：四号谷地满铺为 70×70 + 40×40×3 = 9700 格；一次只渲染活跃基地，DOM 规模与现有单画布完全一致，性能零风险。
  - Alternatives Considered：① 活跃基地全尺寸 + 其余基地缩略图；② 四张画布全尺寸纵向排列。
  - Rejected Because：① 缩略图仍需把其余基地的机器放进 DOM，收益不如页签干净；② 满铺时近万格同屏，拖动明显卡、页面极长。
  - Trade-offs Accepted：同屏看不到其他基地的布局细节。
  - **补偿设计**：每个页签直接标出该基地的 `基地名 · 主/副 · 已放机器数 · 占地/可用格 · 协议容量占用 · 已选目标`，
    扫一眼就能看出整个地区的分布与压力，不用逐张点开。
  - Revisit When：若博士后续希望同屏对比两张画布，再加「并排对比」开关。

- **Decision 3：自由模式保留为独立的"无基地"通道**
  - Reason：既有 802 条回归锁与博士的日常用法都建立在单画布语义上；把它并入多基地会引入"伪基地"概念，污染数据模型。
  - Trade-offs Accepted：两条路径（自由模式 / 多基地模式）需要各自维护一套渲染分支。

### 4.4 验收证据

- `test_html.js` **现有 802 条全部保持通过**（单基地行为零回归）+ 新增多基地断言（状态层可在测试沙箱内验证：切基地后内容保留、各基地撤销栈独立、清空作用域隔离）。
- `test_layout_events.js` 现有 106 条保持通过。
- 浏览器实测：选谷地 → 四张画布同屏 → 摆件 → 切换 → 切回内容不丢 → 截图留证。

### 4.5 Tasks（Wave 分组）

**Wave 1（状态层，无 UI 依赖）**
- 1.1 多基地状态容器；活跃基地字段对外同形；自由模式兼容通道
- 1.2 切换基地时保存/恢复（含撤销栈、方案、出货口）
- 1.3 跑通现有 802 条回归（必须先全绿再进 Wave 2）

**Wave 2（渲染层）**
- 2.1 该地区全部基地画布呈现（活跃全尺寸 + 其余缩略图，带基地名/主副标识）
- 2.2 点击切换编辑对象 + 当前对象高亮
- 2.3 格子尺寸自适应（保证单张画布宽度不超过容器）—— **未做**：页签模式一次只渲染一张，
  与改造前的单画布完全同构（宽度行为不变、超出时横向滚动），而自动改档会让使用者疑惑「我没动格子怎么变了」。
  保留手动档位（14/20/26/32px）；若要自动适配需明确要求。

**Wave 3（收尾）**
- 3.1 撤销/重做、方案快照按基地隔离的边界用例
- 3.2 新增回归锁 + 浏览器实测 + 截图归档

## 六、决策记录（四项全部已定，2026-09-24）

- **Q1「最快」的口径** ✅ 产量达标是**硬约束**（规划器算稳态满速，不存在「更快」可调）。
- **Q2 多画布呈现方式** ✅ **页签切换（一次一张）+ 页签摘要**。
- **Q3 占地与用电的优先级** ✅ **用电优先**。
- **Q4 第三优化层** ✅ **物流线总长最短**（博士看过对比示意图后确认）。

> **最终口径**：硬约束 C1~C5 → 优化 **用电 > 占地 > 物流线总长**。

### 第 1 期实施记录（2026-09-24 完成，尚未推送）

- **Wave 1 状态层** ✅ `LO.bases` 容器 + 8 个基地级字段（size/objs/sel/viewRot/plan/plans/hubPicks/dlvPop）
  用访问器代理到 `bases[当前基地]` → **142 处引用零改动**；`LbaseSet` 改为纯切换（不再「尺寸变了就清空」）。
- **Wave 2 渲染层** ✅ 该地区基地页签 + 摘要（基地名 · 主/副 · 尺寸 · 机器数 · 占地/可用格 · **容量占用/上限**（超限标红）· 是否已出产线）；
  自由模式不出页签；一次只渲染当前这片（性能与单画布同量级）。
- **Wave 3 收尾** ✅ 新增 8 条回归锁；浏览器实测各基地内容隔离与恢复。
- **验收**：`test_html.js` **810/810**（skip 14）+ `test_layout_events.js` **106/106**；release.py 全链六步全绿。
- **实施中被抓出的真 bug（2 个）**：
  ① `Lapply`（撤销恢复）的赋值顺序 —— 先写 `size` 再切 `base`，会把尺寸写错格子（由本次新增的回归锁抓出）；
  ② **协议容量一直算成 0（既有 bug，且长期未被发现）** —— `Rbandwidth()` 读 `byBp().bandwidth`，
     而 `byBp()` 的「占地蓝图」注入版**不含该字段**（注入层裁剪过），于是页面「📶 协议容量」长期显示 `0/200`、
     超限永不报警。更糟的是**两条既有测试用同一个坏口径算期望值**，所以一直"假绿"（修好后它们才转红、暴露出来）。
     修法：建 `id→bandwidth` 索引改从 `DB.buildings` 取；两条假绿测试的期望值同步改正。
