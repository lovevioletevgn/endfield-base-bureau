# 拆链分基地 —— 实现方案（v171）

> 起草：2026-09-29 · 状态：**✅ 已实现并上线（v171）**
> 触发：博士反馈「中容武陵电池 @10/分 一键生成后画布不显示」的深挖结果。

**✅ 已确认的设计决策（博士 2026-09-29 拍板）**：
- **Q5 = 自动无感** —— 由「一键生成（全地区）」自动拆链，**不新增按钮**。
- Q1（最多切到几个基地）= 上限 4（该地区基地数，推荐值）
- Q2（切点选层）= 贪心（能多塞一层就多塞一层，优先切台数多的中间料）
- Q4（与跨地区收货关系）= 可叠加（先跨地区分地区，再地区内拆链）
- ⭐ **可行性已实测验证**（见 2.2）。

---

## 一、问题本质（已实测取证）

### 1.1 现状：`RbaseBest` 只会「整条链塞一个基地」

```
RbaseBest(targets, region)          # 同地区多基地装箱
  └─ RfitSide(targetId, perMin, size, region)   # ← 关键：判「整条链塞进一块 size×size」
       └─ Rexplode(...) → LawPlan(res, size, ...)  # 整图摆位，不拆
```

**实测（武陵 · 中容武陵电池）**：

| 速率 | `totalMachines` | 四个基地（武陵城 80 / 景玉谷 50 / 首墩 50 / 应龙关 50） |
|------|-----------------|------------------------------------------|
| @5   | 87 台            | ✅ 塞进武陵城                              |
| @8   | 139 台           | ❌ **四个全报「装不下」（kind=capacity）**   |
| @10  | 174 台           | ❌ 全报装不下                              |
| @18  | 312 台           | ❌ 超 `RW_MAX_MACHINES=180`                |

> ⚠️ **v176 起本表台数为历史值**：配方耗时口径修正后（`seconds = progressRound`，原式高估 6 倍），
> 同一目标的台数约为上表的 **1/6** —— 中容武陵电池 @10 为 **35 台**、@18 为 **52 台**。
> 上表记录的是 v171 拆链设计时的实测，保留原样以存真；**当前数值以产物与回归锁为准**。

**为什么 139 台塞不进 13576 格？** 不是面积不够 —— 是 `RfitSide` **把整条链当一个不可分的整体**，
一旦单块画布的布局求解失败就判「装不下」，**从来不考虑把链切开分到多个基地**。

### 1.2 机制依据：同地区基地之间能自由取货（可行）

`docs/数据手册-玩法与物流.md` L153-155：

> 「各地区仓库是**互相独立**的」……**同地区的基地都能从它取货**。
> **粒度是「地区」不是「基地」**：一个地区的几片基地**共享该地区这一个仓库**，不是每个分基地各配一个仓库。

⇒ **A 基地做中间品 → 进地区仓库 → B 基地用「取货口」从仓库取货接着做** —— 机制成立。

⭐⭐ **关键简化（2026-09-29 核实）**：**不需要在基地之间铺传送带/管道**！
同地区基地共享仓库 ⇒ 基地间的物料流转**完全走仓库**（A 产出进仓库 → B 取货口取）。

**这与项目已有的「跨地区收货」是同一个机制**，只是跨度从「谷地↔武陵」缩短成「同地区基地间」。
**最大的好消息**：`Rexplode` 的 `shipInList`（收货清单）**已经是现成的「外部输入」通道** ——
我们只需要让「同地区基地收货」也走这条通道，**产线展开 / 摆位 / 连线 / 报告全部零改动**。

## 二、方案设计

### 2.1 核心思路：**把「装不下的链」按层截断**

```
现在：  目标(中容武陵电池@10)  ──14 层──►  原料（源矿/蓝铁矿/砂叶…）
        └─ 一个基地，塞不下 → 报「装不下」

改后：  目标(中容武陵电池@10)
        ├─ 基地 A（武陵城 80×80）：只做「下游 N 层」到某个截断点
        │    └─ 截断料 X 标「同地区基地收货」← 走 shipInList 通道（零改动）
        └─ 基地 B（景玉谷 50×50）：做「截断料 X + 它上面那层」
             └─ 再截断 → 基地 C ……（直到原料层/装得下为止）
```

**关键：截断点上那根料，对下游基地就是「外部输入」** —— 直接复用 `shipInList` 机制，
`LawRun` / `Rexplode` / `LawPlan` / `RwRoute` / `RwRoute` / 报告渲染**全都不用改**。

### 2.2 可行性已实测验证（2026-09-29 探针）

**切链后每段能否摆下 —— 实测结果（中容武陵电池 @10/分）**：

| 方案 | 台数 | 武陵城 80 | 景玉谷/首墩/应龙关 50 |
|------|------|-----------|----------------------|
| 不切（现状） | 174 | ❌ | ❌ |
| 切「壤晶 + 致密源石粉末」 | **10** | ✅ | ✅ **全部能摆** |
| 只切「致密源石粉末」 | 40 | ✅ | ❌ |
| 切「壤晶+致密源石粉末+源石粉末+砂叶粉末」 | 10 | ✅ | ✅ |

⇒ **拆链可行，且效果显著**：把壤晶与致密源石粉末当外部输入后，下游段只剩 10 台封装机，
**任何基地都能摆下**。

⭐⭐ **实测抓到的关键实现前提**：现有 `RfitSide(targetId, perMin, size, regionName)`
内部写死 `Rexplode(targetId, perMin, {region:regionName})` —— **不带 `shipInList`**。
⇒ 探针一开始误报「切链后仍摆不下」就是这么来的（它重新做了完整展开）。
**`RsplitChain` 必须给 `RfitSide` 加一个 `shipInList` 参数**（或内部改用带截断的展开），
否则判据与真实落画布**不同源** = `RbaseBest` 的老毛病重演。

### 2.3 拆链粒度：按「层的深度」切，而不是按机器数切

- `Rexplode` 已经把整链组织成**分层树**（`res.machines[].depth`）。
- 天然切点：**层的边界**（同层机器不拆到两个基地 —— 避免同层物料跨基地来回跑）。
- **切在第几层** 由「该基地 `RfitSide` 最多能吃到第几层」决定（贪心：能多塞一层就多塞一层）。

⚠️ **代价必须如实告知**（已写进产品口径的既有约束）：
**分到不同画布必然各建一套**。若截断料 X 在 A/B 两个基地都要用，则 **X 及其上游会在两个基地各建一遍**
（因为不同画布是独立产线，地区仓库只共享「成品/中间品」，不共享「正在运行的机器」）。
→ 报告里要**明确列出重复建了哪些料**（`dupShared` 机制已有，复用）。

### 2.3 三档能力（建议**先做档 1**，档 2/3 看效果再定）

| 档 | 能力 | 复杂度 | 建议 |
|----|------|--------|------|
| **1** | **同基地内多目标**已有的不动；新增「一条链按层切到 N 个同地区基地」，每基地一段，截断料走 shipIn | 中 | ⭐**先做这个** |
| 2 | 切点自动最优化（搜索「切几下、切在哪」使总占地最小） | 高 | 看档 1 效果 |
| 3 | 跨地区 + 同地区混合拆（谷地做一段、武陵做一段、武陵内部再拆） | 高 | 远期 |

### 2.4 改动清单（档 1）

| 文件/函数 | 改动 | 说明 |
|-----------|------|------|
| `RbaseBest(targets, region)` | **改**：`RfitSide` 失败时，不再直接报「装不下」，而是**尝试切链**（新增 `RsplitChain`） | 主改动点 |
| **新增** `RsplitChain(targetId, perMin, bases, region)` | 返回 `[{levelId, cutItems:[...]}]` | 切链求解器 |
| `RfitSide` | **改（小）**：加 `shipInList` 参数，传给 `Rexplode` | ⚠️ **必需** —— 否则判据不同源（见 2.2） |
| `Rexplode` | **不改**（`shipInList` 已支持任意物品当外部输入） | 零改动 |
| `LapplyAssign` / `LapplyAssignAll` | **小幅改**：落画布时把「截断料」写进该基地的收货源 = 上游同地区基地 | 收货对齐 |
| 报告 `RbaseBestHtml` | **加一段**：「拆链方案」清单（哪段在哪基地 / 截断了什么料 / 重复建了什么） | 透明化 |
| 测试 | **+N 条锁**：切链后①每段真能摆下 ②截断料出现在上游基地产出清单 ③重复建如实列出 | 防假成功 |

### 2.6 切链算法（贪心，草案）

```
RsplitChain(targetId, perMin, region):
  ① 拿 region 的基地列表，按「主基地优先 + 可用格降序」（与 RbaseBest 同序）
  ② 剩余待分链 = 完整链；对每个基地（从大到小）：
       a. 从「剩余链」的根开始，尝试逐步把「上游料」加进 cutItems（= 当外部输入）
       b. 每加一个就试摆（RfitSide + shipInList）—— 一旦能摆下，就定这个基地的 cutItems
       c. 拿到该基地的「截断清单」后，剩余链 = 这些截断料及其上游（继续给下一个基地）
  ③ 全部基地试完仍切不干净 → 如实报「拆链后仍装不下」
```

**切点优先选「台数多的中间料」**（贪心按 `machines` 降序加），因为这样能最快把下游瘦下来。

### 2.5 硬边界（必须写进代码注释 + 报告）

1. **切链只在「整条塞不下」时启动** —— 塞得下就维持现状（老路径零改动，回归不受影响）。
2. **截断料必须在同地区仓库可流转**（同地区基地共享仓库 —— 已核实机制成立）。
3. **同层不拆** —— 切点只能在层边界，避免同层物料跨基地往返。
4. **重复建如实告知** —— 不同画布必然各建一套，报告要点名。
5. **失败不清场**（v170 刚修的 `LawFail` 要继续用）—— 切链失败也要干净退回。

## 五、工作量评估

- `RsplitChain` 求解器：核心难点（要复用 `RfitSide` 多次试摆，注意性能 —— 每次 `Rexplode` 10~300ms）。
- 估计改动 `build_html.py` 约 150~250 行新增 + 30 行修改。
- 建议**先做一版最小可用**（Q1=上限 4、Q2=贪心、Q3=只标「从 X 基地取」），跑通后再迭代。
