> 参考站点：`ef.yituliu.cn/tools/power-calc`（电池分流）、`factory.ef.yituliu.cn/aef`（产线量化，FactorioLab 引擎 fork）。

## 一、结论先行

**产线算法主体不需要改**，但**「发电」这块有一个真缺口值得补**：项目只报「需要几台热能池」，
不报**燃料供给速率**、不校验**喂料传送带够不够**、也没有「超喂＝废料」的提示。
参考站恰恰把这三件事做成了核心（它的整个 UI 就是一棵**分流器树**）。

**没有发现任何「算错」** —— 台数公式经数学证明两者恒等（见 §三）。
差异全部是**「项目没输出的信息」**与**「建模粒度」**，不是错误。

## 二、参考计算器反解（实测）

### 2.1 电池分流计算器（power-calc）

懒加载组件 `_nuxt/avII-Xr5.js`，核心函数 `I()`：

```js
// w = 电池输出速度(个/分)  c = 其他来源电力  S = powerPerBattery  B = burnTimeSeconds
// e = 所有 thermal 节点的 rate 之和（⚠ 关键：节点 rate 由「分流器树」自上而下均分）
_.value = e;                      // 燃烧电池速率（个/分）
const a = B/60;                   // 每烧一个电池耗时（分）
M.value = e * a;                  // → 需要热能池个数（实数）
V.value = Math.ceil(M.value);     // 向上取整台数
A.value = M.value * S;            // 平均输出功率
J.value = A.value;                // 平均输出功率
ae.value = A.value + c;           // 总电力
```

**燃料数据（与项目逐项一致）**：

| 燃料 | 燃烧时间 | 功率值 |
|---|---|---|
| 源矿 | 8 秒 | 50 |
| 低容谷地电池 | 40 秒 | 220 |
| 中容谷地电池 | 40 秒 | 420 |
| 高容谷地电池 | 40 秒 | 1100 |
| 低容武陵电池 | 40 秒 | 1600 |
| 中容武陵电池 | 40 秒 | 3200 |

UI 形态：**输出口 →（拖入）分流器 / 热能池**，构成一棵树；分流器每级把速率均分给子节点。
「其余电池认为送回仓库」——即**超喂的部分不进发电**。

### 2.2 产线量化计算器（aef）

`github.com/endfield-calc/factoriolab` 的构建产物，基于 **FactorioLab 引擎**。
核心是 **线性规划（LP）全局求解**：给定目标产量，同时解出所有机器数、所有物料流，
天然处理**副产物回流、循环、多目标共享**。UI 直接给「每分钟」速率与净产量。

## 三、逐项对账

### 3.1 台数公式 —— 恒等，不是差异点

| | 项目 v169 | 参考 |
|---|---|---|
| 公式 | `ceil(缺口 ÷ 燃料功率值)` | `ceil(烧速 × 燃烧秒数 ÷ 60)` |
| 例（武陵缺 31800） | 31800÷1600 = **20 台** | 29.81×40÷60 = **20 台** |

**数学证明**：参考里「台数 = 烧速 × B/60」，而「台发电 = 单台烧速(60/B) × B/60 × S = S」。
所以「达到缺口需要烧速 = 缺口/S」，台数 = 缺口/S × B/60 = 缺口/S（因单台烧速×B/60=1）。
**两者恒等**。→ 项目台数算得对。

### 3.2 真实差异（4 处）

| # | 差异 | 参考 | 项目现状 | 影响 |
|---|---|---|---|---|
| ① | **燃料供给速率** | 明确输出「烧掉 N 个/分」 | 只报台数 | 玩家不知道每分钟要喂多少料 |
| ② | **喂料传送带** | 分流器树显式表达 | 完全没建模 | 不知道要几条带喂料、会不会堵 |
| ③ | **超喂＝废料** | UI 天然体现（多余送回仓库） | 无提示 | 玩家可能误以为「堆料＝发更多电」 |
| ④ | **全局求解** | LP 全局最优 | 贪心递归（`Rexplode`） | 多目标/副产物回流时可能非最优 |

### 3.3 项目已做对、无需动（3 处）

1. **燃料数值 6 项全部对齐**（见 2.1 表）。
2. **带 / 管吞吐已建模**：`RW_BELT=30`、`RW_PIPE=120`，`RwLines()` 算线数、`RflowAudit` 做吞吐体检 —— 只是**没接到发电的燃料供给上**。
3. **副产物 / 回收 / 闭环自持已具备**：C6-b 副产物入图、`pick()` 三级降级、`selfLoop` 开关。

## 四、建议（待博士拍板，均属新功能）

### 建议 A（低风险，强烈推荐）：发电报告补「燃料速率 + 带数」

在现有 `Rtheories` / `RgenPlanOf` 输出上追加两个派生量，**不改任何现有算法**：
- `burnPerMin` = 缺口 ÷ (燃烧秒数/60) ÷ …（等价于台数 × 单台烧速）
- `beltsNeeded` = `ceil(burnPerMin ÷ 30)`

并在报告里加一句硬提示：**「每台热能池只烧 1.5 个/分（电池）· 7.5 个/分（源矿），
堆料不会多发一度电；多余燃料请在分流器上分流回仓库。」**

数据已齐（`fuelPower[].seconds` 字段现成，只是没被算法使用）。

### 建议 B（中风险）：绘制「燃料供给分流树」

把参考站的「分流器树」可视化搬进来：从燃料源到 N 台热能池，显示每条带带几台。
本质是复用项目已有的布局/布线引擎 —— 但**改动面中等**，且要新增一套"发电区"布局。

### 建议 C（高风险，暂不建议）：LP 全局求解

本项目是「排版器」不是「求解器」，`Rexplode` 的贪心递归是核心资产（601+ 回归锁依赖）。
换 LP 会推翻几乎全部回归基线。**除非出现明确的「贪心算错」实锤，否则不换。**
