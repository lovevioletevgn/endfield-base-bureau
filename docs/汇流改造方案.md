### 一·补、⭐ 自适应原则（博士 2026-10-20 05:57 追加）

> 原话：「**以合理排布为准，比如小基地可能用不到两侧，摆一侧也可**」

⇒ **不是强制分两片**。分几片由「剩余空间够不够」决定，不写死。

**正确的决策顺序（这是本节的核心）**：

1. **先给「进货端」占位** —— 基段 + 取货口是**功能必需**，不能被机器挤掉。
   （v203 的致命错误就是「先把机器铺满整张画布，再去找基段位置」，结果 `feeder=0`。）
2. **再给「出货端」占位** —— 末级机器外侧那段留给箱子和出货线。
3. **剩下的空间**按贴块逻辑摆机器。
4. **分片判据**：单片装得下就**不切片**（简单、线短）；装不下才切成两片，基段移到中间。
   - 小基地（谷地副 40×40 / 武陵副 50×50）通常一片就够；
   - 大基地放长链（本场景 35 台 / 80×80）才需要两片。

⚠️ **判据必须用「真试摆」而不是面积估算** —— 与 `RfitSide` 同一口径（v159 的教训：
面积估算系统性低估 2~2.5 倍，会判「装得下」然后实际摆不下）。

### 二、为什么这个设计能一次解决三个死结

| 死结 | 现在（v203 单片区）| 基段居中后 |
|---|---|---|
| **进货端** | `feeder=0`、基段 0 段（机器铺满画布，右侧没地方）| 基段横在中间，**两侧都能贴取货口**，取货口紧邻机器 |
| **出货端** | 出货线 18 格 + 6 格串进产线带（箱子周围被产线线夹死）| 箱在画布两端，**外面再没有东西**，出货线只剩几格 |
| **线长** | 整条链竖向贯穿 40+ 行 | 每条子线只走**半个画布** |

### 三、关键几何事实（已从配置表核实）

| 件 | 尺寸 | 端口 | 可旋转 |
|---|---|---|---|
| `log_hongs_bus`（存取线基段）| **4×8** | — | ✓ 旋转 90° 变 **8×4**（横向）|
| `log_hongs_bus_source`（源桩）| 4×4 | — | ✓ |
| `unloader_1`（仓库取货口）| **3×1** | output (1,0) 朝**上** | ✓ 旋转 180° 后 output 朝**下** |

⇒ **基段转 90° 横放，上沿贴一排取货口（朝上供上片）、下沿贴一排（转 180° 朝下供下片）。**

### 四、实现路径（下一版直接照这个做）

1. **分片**：按 depth 把实例**对半切**（`每节点取 ceil(n/2)` 给上片、`floor(n/2)` 给下片）。
   实测本场景对半分得干净：封装机 2→1/1、研磨机 8→4/4、粉碎机 16→8/8、提纯机 4→2/2、反应池 2→1/1。
2. **基段**：横放在画布中部（`y ≈ size/2`），占一整条横带；源桩接在一端。
3. **上片**：从基段上沿起，**depth 大的靠基段、depth 0 在顶部**，末端接协议储存箱。
4. **下片**：从基段下沿起，**depth 大的靠基段、depth 0 在底部**，末端接协议储存箱。
   ⚠️ 两片内部仍用「贴块」逻辑（上游贴下游、中间隔 1 格），但**各自独立计算**，不要写死镜像。
5. **取货口**：上片取货口贴基段上沿朝上；下片贴基段下沿朝下（`rot` 180°）。

### 五、验收

- `probe_v203_feed.js`：`feeder ≥ 4`、`bus` 的基段 ≥ 3 段
- `probe_v203_store.js`：出货线 **≤ 8 格**
- `probe_v203_broken.js`：最严口径 @10 断头不高于 v202 的 5
- 四件套：`test_html` 全绿（当前 1031/1033，2 条出货线锁待转绿）+ 事件层 106 + check_docs

## ⛔ 2026-10-20 03:30 复核结论：**本方案的前提不成立，暂停执行**

> 复核方式：只读侦察（探针在 `_archive/probe_v203_*.js`），**产品代码零改动**。
> 完整证据 → `.workbuddy/memory/2026-10-20.md`「03:30 复核」节。

**一句话**：汇流器 `log_converger` 的吞吐 = **2000ms/轮 = 30/分 = 一条传送带的满载吞吐**。
它把 3 条带子并到 1 个**端口**，但**不提高吞吐**。本场景每台机器都满速（30/分），
所有支线之和远超 30/分 ⇒ **汇流后主干必堵**，线格数**一格都不会少**。

| 事实 | 数据 | 来源 |
|---|---|---|
| 汇流器端口 | **3 进 1 出**（进：90/180/270；出：180） | `raw/FactoryGridRouterTable.json` |
| 汇流器吞吐 | 2000ms/轮 = **30/分** | 同上 `msPerRound` |
| 传送带吞吐 | 2000ms/轮 = **30/分** | `raw/FactoryGridBeltTable.json` |
| battery_5@10 源石粉末需求 | **480/分**（16 台粉碎机 × 30/分） | `res.machines[].perMachine` |
| ⇒ 物理必需线数 | **16 条** | 480 ÷ 30 |
| 实测 `route.stats.merge` | @10 = **0**，@30 = **5** | 探针 |

⚠️ **§四·补 那条「2 进 3 出」的疑问是读错了表**：`inputPorts` 有 **3** 条记录、`outputPorts` 有 **1** 条，
原先误把两个数组的条数读反。代码里 `RW_MERGE_FANIN=3` 与 `build_html.py:1333` 的回代注释**都是对的**。

**`useMerge=0` 不是 bug，是算法正确判定「这一段不需要并、也不该并」。**

### 复核后真正可行的三条路（待博士拍板）

- **甲｜束化**（低风险）：同源同汇的多条线走**相邻平行走廊**，视觉从「散成一片」变「并成一束」。线格不变。
- **乙｜贴块短接**（高风险，收益最大）：上游**出料口外侧格**正好落在下游**进料口格**上 ⇒ 0 格带子。
  `LawPlan` 要从「按层排行」改成「按依赖贴块」，回归锁全重定标。
- **丙｜只放开 `corr`**（不建议）：线格 1919→844（-56%），代价手动连 2→10，且全是跨画布 50 格的长线。

### 复核时顺带查出的两个真问题（比「乱」严重）

1. **@10 源石粉末段已超载**：13 条扛 480/分 ⇒ 36.9/分/条 > 30 ⇒ 该段永远堵，产线跑不满。
2. **@30 有 56 条线没铺出来**（`warns` 里 56 条「手动连」，源石粉末段第 22~40 条等）⇒ @30 画布是**残的**。
3. **砂叶粉末的粉碎机每台 90/分**（需 3 条带/台），而 `RwLines(240,false)=8` 按总需求算 ⇒ 3×3=9 才对，永远差 1 条。

## 一、问题定义（先看清「乱」是什么）

不是「某处断了一截」，而是**线的数量本身太多**。

**实测数据**（`battery_5` @10，80×80 画布）：

| 项 | 数量 |
|---|---|
| 画布总格 | 6400 |
| `link`（产线内部走线） | **1950 格** |
| `feedlink`（进料线） | 343 格（v202 后 377） |
| `sinklink`（销毁线） | 57 格 |
| **线合计** | **≈ 2350 格 ≈ 画布 37%** |

⇒ 视觉上必然是蜘蛛网。**重构 UI 不解决**（格子/箭头渲染都正常，乱的是拓扑）。

## 二、根因（架构级，不是 bug）

早期规则（记忆原话）：
> 「一个取货口只有 1 个出料口、只能接一条带子」+「N 台机器吃同一种原料，就摆 N 个口」
> —— 第一版**不做分流器**，简单可靠、不静默丢料。

⇒ 每台机器 / 每个取货口都拉一条**独立**线 ⇒ 机器一多，线成倍增长。

## 三、⭐现有能力盘点（开工前必读，别重复造）

| 能力 | 现状 |
|---|---|
| **汇流器** | ✅ **有** —— `log_converger`「汇流器」（1×1 · `type:Router` · 传送带 · **30/分**）<br>`inputPorts` 2 个（facing **90 / 180**）· `outputPortCount` **3**（facing **90 / 180 / 270**） |
| **管道汇流器** | ✅ `log_pipe_converger`「管道汇流器」（1×1 · `FluidRepeater` · **120/分**） |
| **分流器** | ✅ `log_splitter` / `log_pipe_splitter`；`rt.belts` 有 `bl.split`，落盘有 `planRole='split'` 分支 |
| **落盘分支** | `rt.belts` 的 `bl.merge` 会落成 `planRole='merge'`（`LawRun` 两处分支都在）——**但上游从未产出 `merge` 标记**，这才是缺口 |

> ⚠️ 2026-10-20 03:15 我曾错误地断言"没有汇流器"——原因是只搜了 `merge`，
> 而实际命名是 **`converger`（汇流 = converge）**。**教训：找东西要按语义多试几个词根，别只认一种命名。**

## 四、⭐改造的关键约束（非常重要）

1. **吞吐上限**：`log_converger` = **30/分**。汇流后主干流量 = 各支线之和，**不得超过 30/分**。
   ⇒ 只有「支线流量之和 ≤ 30/分」的组合才能合并；高速产线必须分流成多条主干。
2. **端口朝向**：输入 2 面（90/180）、输出 3 面（90/180/270）⇒ 合并点要按朝向摆，不能任意放。
3. **不能只改渲染**（少画几笔 = 把问题藏起来，不解决）。
4. **不能全局改寻路代价**（v202 的教训：全局 soft 会挂无关锁）。

## 四·补、⚠️ 仍建议开工前跟博士核一句

> **汇流器是「2 进 3 出」还是「任意面进出」？**（`inputPorts` 只列了 2 个面，但 `type:Router` 暗示可能更灵活）

这条不影响方案框架，只影响合并点的摆放判据。**先问一句，别像上次「管桥能不能叠带」那样猜错。**

## 五、改造思路（假设「能自然汇入」）

### 5.1 目标
同方向的 N 条支线 ⇒ **1 条主干 + 短支线**，线格数目标下降 **≥40%**。

### 5.2 落点（按优先级）
1. **`RwRoute` 的合并点选取**：对同向、相邻、终点相近的多条线，在**下游某格**合并。
   - 候选合并点：主干上离各支线终点最近、且不额外增加交叉的格。
   - ⚠️ 合并后主干承载 N 路流量 ⇒ 需检查**吞吐**是否成瓶颈（记忆：「运输真实吞吐」仍是未测量项）。
2. **`RplaceFeeders`**：多个取货口送同一种原料时，先汇入一条主干再进产线（当前是 N 条独立）。
3. **`rt.belts` 的 `merge` 标记**：若确认存在「汇流」语义的落盘件，接上落盘分支。

### 5.3 ⚠️ 红线（别踩）
- **不能只改渲染**（少画几笔 = 把问题藏起来，不解决）。
- **不能牺牲连通性**：合并后必须逐格验证「同介质连通」，用 `probe_strict.js`（严格口径）。
- **不能全局改寻路代价**（v202 的教训：全局 soft 会挂无关锁）。

## 六、验收（缺一不可）

1. **线格数**：`battery_5@10` 的 `link+feedlink+sinklink` 从 ≈2350 降到 **≤1400**。
2. **断头不增加**：`probe_strict.js` 严格口径，battery_5@10 / @30 / copper_nugget@30 / battery_3@10 全 0（管桥格除外）。
3. **四件套全绿**：日常 1033/1033 · HEAVY 1047/1047 · 事件层 106/106 · check_docs。
4. **视觉终验**：截图对比，机器区周围不再是平行带状堆叠。
